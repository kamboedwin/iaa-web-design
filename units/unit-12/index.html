01 / Getting started

Learning outcomes

A webpage can look complete on your computer but still be invisible to people elsewhere. Publishing gives other people a way to open it using a web address. For a library or records centre, a published site is also a responsibility: visitors depend on accurate information, safe access and working links.

By the end of this unit, you should be able to:

  1. Explain hosting, domain names, DNS, web servers, HTTPS and deployment.
  2. Differentiate static hosting, content management systems and managed web applications.
  3. Compare free and paid hosting in terms of purpose, limitations, support and ongoing costs.
  4. Describe the basic process of publishing a small static website using GitHub Pages.
  5. Use a simple checklist to evaluate a website before and after publication.
  6. Identify maintenance, privacy, copyright, accessibility and security responsibilities for information institutions.
Connection to earlier units: HTML gives a webpage structure, CSS styles it and JavaScript adds basic interaction. Hosting is how those files can be delivered to visitors over the web.

03 / Core concepts

From local files to a public webpage

When you create index.html on your computer, your web browser can display it, but another person cannot automatically reach it over the Internet. A published website places its files or application on an Internet-connected hosting service.

Web hosting is a service that stores website files or runs a web application so that visitors can access it. A web server receives requests and returns resources, such as HTML pages, stylesheets and images. Deployment is the process of placing a working version of the website on a hosting service.

Library example: A public library publishes its opening hours, staff contacts and service descriptions. Records example: A records centre publishes general enquiry procedures. The public webpages can be simple, even if restricted institutional records are stored in separate protected systems.

04 / Understanding addresses

Domains, DNS and web addresses

A domain name is a human-readable name associated with an Internet service, such as example.org. A domain is not the same as the website files and is not the same as hosting. Names are registered through domain registrars; renewal and use are governed by the applicable registration arrangements.

DNS (Domain Name System) translates a name into the information needed to locate its Internet service. For example, an A record points a hostname to an IPv4 address, while a CNAME record aliases one hostname to another. The exact records depend on the provider's instructions.

05 / Protecting connections

HTTP, HTTPS and certificates

HTTP is a protocol browsers use to exchange web resources. HTTPS adds transport encryption through TLS, helping protect information in transit and authenticate the website connection using a certificate. Browsers commonly show a connection indicator for HTTPS.

HTTPS is important, but it does not guarantee that an organisation is trustworthy, that a form stores data securely or that confidential records have suitable access controls. Those require additional safeguards.

Practical rule: never enter real login details or personal records into a practice form. For a real institution, protected information must be handled using approved services, proper authentication, authorisation, secure storage and relevant policies.
06 / Hosting options

Choosing the right kind of hosting

Hosting is not a single product. Different websites require different levels of functionality, administration and cost.

Common approaches to web publishing
OptionSuitable forImportant limitations
Static hostingHTML/CSS/JS websites, public guides, portfoliosDoes not independently provide server-side accounts, secure processing or a records database
Hosted site builder or CMSPublic notices, articles and frequently updated informationFeatures, user permissions, updates, pricing and support vary by service
Shared or managed application hostingSites using compatible server software and databasesNeeds updates, backups, access control and ongoing administration
Cloud or institution-managed serviceMore complex or integrated applications with specific requirementsNeeds technical support, governance, security planning and cost management

Examples: GitHub Pages and Cloudflare Pages serve static websites; WordPress-based hosting can support content-managed sites; specialist library or records-management systems generally need hosting and support matched to their application and security requirements.

07 / Compare providers

Free versus paid hosting

Free hosting can be excellent for a simple educational website. It may provide a provider-supplied address, HTTPS and basic static deployment. However, free services may impose size, traffic, usage, build, bandwidth or acceptable-use limits; policies can change.

Paid hosting may offer custom service levels, database support, backups, technical support, email or additional storage, but a paid plan does not automatically make a website secure or well designed. Before selecting a provider, check:

  • Purpose: Is the site a public guide or a confidential transaction system?
  • Technical needs: Does it require server-side processing, database access or staff accounts?
  • Costs: What happens after introductory pricing, domain renewal or usage growth?
  • Reliability: What support, backup and recovery arrangements are offered?
  • Ownership: Who controls the domain, files, data and account?

Provider features and prices vary; always check current official terms rather than assuming a service remains free for every use.

08 / Worked example

How GitHub Pages publishes a static website

GitHub is a service used to store and manage code in repositories. GitHub Pages can publish static HTML, CSS and JavaScript from a repository. A simple site must have an entry page such as index.html, and its paths must be correct.

  1. Organise the website: keep index.html at the chosen publishing source root and store supporting files in clearly named folders.
  2. Create a repository: for a basic personal GitHub Free Pages site, use a public repository.
  3. Add the website files: upload the real files, not just a ZIP archive containing them.
  4. Choose publishing settings: open repository Settings → Pages, select Deploy from a branch, and choose the desired branch and root directory.
  5. Open and test: use the published URL, verify the navigation, images and mobile layout, and correct any broken links.
Important: GitHub Pages is intended for public static websites. A private repository does not, by itself, make its published Pages website private. Never publish confidential records or credentials in source files.

Example project structure:

library-services/
├── index.html
├── services.html
├── css/
│   └── style.css
└── images/
    └── library.jpg

For a repository site, the final link usually follows a pattern such as https://username.github.io/repository-name/. Replace the placeholders with the real account and repository names.

09 / Common errors

Relative links when a website goes online

Some pages work locally but fail after publication because their links point to the wrong location. A relative path describes a location from the current file; an absolute path begins from a fixed root or full URL. If your website is published in a GitHub Pages project subdirectory, a leading slash may point to the wrong root.

Paths when the file index.html is beside the css folder
CodeExplanation
href="services.html"Links to a page beside index.html
href="css/style.css"Finds CSS inside the css folder
src="images/library.jpg"Finds an image inside the images folder
href="/services.html"Starts from the domain root; may fail for a repository subpath

Always test the website from its published address. Links to files on a personal computer, such as C:\Users\Student\Desktop\..., will not work for other visitors.

10 / Beyond one platform

Other publishing routes and institutional systems

There is no single hosting option for all websites. For a static project, services such as Cloudflare Pages or Netlify can publish HTML, CSS and JavaScript through supported deployment methods. A no-code or CMS platform may make it easier for authorised staff to maintain public announcements. A full library catalogue or electronic records-management system requires appropriately configured application hosting and institutional controls.

Public library website: a static site may be enough to publish hours, rules and contacts, while linking to a separately hosted catalogue. Records centre: a public guidance site should be separated from restricted staff records processing.

A professional hosting decision involves staff skills, updates, backups, service continuity, legal obligations and the institution's information-management policies—not only the initial price.

11 / Keeping a service useful

Website maintenance and responsibilities

Publishing is not the end of a website's life. A useful website needs named responsibilities and a review schedule. Library opening hours, service contacts, collection links and public records procedures can become misleading when left outdated.

Example maintenance checklist for an information-service website
AreaTypical check
AccuracyAre opening times, addresses, service guidance and links current?
AccessibilityCan visitors use headings, keyboard navigation, readable contrast and meaningful link labels?
SecurityAre accounts protected, software updated, permissions reviewed and sensitive data excluded from public files?
ContinuityAre domain renewals, backups, recovery procedures and support contacts clear?
Privacy and ownershipDo public materials have permission to be published? Are personal and restricted records properly protected?

Professional roles: information specialists may maintain content, metadata, accessibility and records policies; technical staff may administer infrastructure, security and software updates. Both groups need to coordinate.

18 / Bring it together

Unit 12 summary and further reading

  • Hosting makes website resources available to visitors over the Internet; publishing moves the working site into the hosting environment.
  • A domain provides a human-readable name; DNS helps direct visitors to the right service; a URL identifies a particular resource.
  • Static hosting is useful for public information pages but cannot alone provide trusted server-side processing for confidential records.
  • GitHub Pages is one method for publishing static sites; paths and deployment settings must be checked.
  • HTTPS protects transport but does not replace safe access control, privacy safeguards or good content.
  • Websites require ongoing content maintenance, accessibility checks, secure administration and institutional responsibility.
