01 / Start here

What you will learn

A website is useful only when people can achieve their purpose. A library visitor may need to find a book; a records-centre visitor may need to understand how to request a public document. Attractive colours cannot compensate for an unclear path to the information they need.

By the end of this unit, you should be able to:

  1. Explain usability, user experience (UX), user interface (UI) and web accessibility.
  2. Describe practical principles of clear navigation, readable content, feedback and consistency.
  3. Evaluate a library or records-service webpage using a simple checklist and a realistic visitor task.
  4. Identify common accessibility issues such as missing labels, weak contrast and inaccessible keyboard controls.
  5. Write short, specific recommendations to improve a webpage.
Connection to earlier units: Unit 2 introduced good design; Units 3–8 showed how HTML and CSS create webpage content and layouts. This unit checks whether those choices actually help users.

03 / Begin with usefulness

What makes a website usable?

Usability concerns how effectively, efficiently and satisfactorily a particular group of people can complete tasks in a particular context. A page may work technically and still be frustrating to use. For example, a book catalogue may load quickly but hide its search box under an unfamiliar menu label.

TermMeaningExample
User interface (UI)Controls and visual elements people interact withSearch box, menu, buttons, text labels
User experience (UX)The broader experience of using a serviceWhether a visitor feels confident after finding information
UsabilityHow well a user achieves a taskFinding library hours without confusion
AccessibilityEnsuring content and controls can be used by people with disabilitiesKeyboard-operated navigation and correctly labelled forms

These ideas overlap but are not identical. A friendly-looking interface is not automatically usable or accessible. The user’s task provides a better starting point than personal preference for colours or shapes.

04 / Identify the visitor

Users, tasks and context

Before evaluating a website, identify who is using it, what they want to achieve, and where or how they use it. This turns a vague opinion into a useful test.

Library example

User: a student on a phone.
Task: find the library opening hours.
Context: limited time before travelling to campus.

Success: the correct hours are easy to locate and read.

Records-centre example

User: a member of the public.
Task: understand which public records can be requested.
Context: unfamiliar with professional terminology.

Success: the request steps and eligibility are written plainly.

Real evaluations may involve several types of users. A single task is a helpful starting exercise, not a complete investigation of all needs.

05 / Design for real people

Seven practical design principles

  1. Clarity: use words visitors understand; make the next action obvious.
  2. Consistency: keep menus, labels and familiar controls predictable across pages.
  3. Feedback: tell visitors whether an action succeeded, failed or needs attention.
  4. Visibility: place frequently used services where users expect them.
  5. Efficiency: reduce unnecessary steps for common tasks.
  6. Error prevention and recovery: give clear instructions and useful messages when something goes wrong.
  7. Inclusiveness: keep the service readable and operable for different abilities and devices.
Example: instead of a button labelled “Process RQF-02”, use “Request a Public Record”. The label describes the action rather than an internal office code.
06 / Organise and name content

Navigation and information architecture

Information architecture is the organisation and labelling of content so people can find what they need. Navigation is the set of links and menus that helps visitors move through that structure.

Less helpful labelClearer labelWhy it helps
LIS OPAC ServicesSearch the CatalogueNames the visitor’s task
RMD Form 17BRequest a Public RecordReduces unexplained abbreviations
GeneralitiesOpening HoursMakes practical information predictable

For a simple service website, a clear main menu might be Home · Services · Catalogue/Records Guide · Contact. Keep important links visible and consistent. If a page has many sections, use descriptive headings and sensible grouping rather than placing everything in one long undifferentiated list.

Search and filtering can help large collections, but they should not be used to hide straightforward information that visitors expect to see immediately.

07 / Help visitors scan

Readability, visual hierarchy and consistency

Visual hierarchy uses heading size, placement, spacing and contrast to guide attention. For example, a library’s search box and opening hours may deserve more prominence than an institutional history paragraph.

Readability involves plain language, short sections, readable font sizes, sensible line lengths and sufficient contrast. Avoid tiny grey text, long blocks in ALL CAPITALS and decorative fonts in body paragraphs.

A consistent design uses familiar button styles, heading levels and navigation locations on every page. Too many different styles make the site harder to learn.

08 / Include more visitors

Accessibility essentials

Web accessibility helps people with different abilities perceive, navigate, understand and interact with content. W3C’s Web Content Accessibility Guidelines (WCAG) summarise four broad principles: Perceivable, Operable, Understandable and Robust.

Perceivable

Provide meaningful text alternatives for informative images and keep text easy to see or hear.

Operable

Make essential controls usable with a keyboard and show a visible focus indicator.

Understandable

Use clear instructions, predictable navigation and helpful error explanations.

Robust

Use valid, meaningful HTML so assistive technologies can interpret content reliably.

Simple checks you can perform: press Tab to move through interactive controls; look for a visible focus outline; zoom the browser; verify images have appropriate alternative text; check that every form field has a visible label; and ensure errors are explained in words, not colour alone.

Important limitation: a quick visual checklist is not proof that a website meets WCAG. Formal accessibility assessment requires more extensive testing, including assistive technologies and applicable success criteria.
09 / Make actions understandable

Forms, feedback and error messages

A form needs clear field labels, concise instructions and helpful feedback. A records enquiry may ask for a request category and contact method; it should not ask for private details unless they are genuinely necessary.

Weak feedback

“Error 430.”

The visitor cannot tell which entry caused the problem or how to correct it.

Better feedback

“Enter a contact email in the format name@example.com.”

The message identifies the field and explains the correction.

A visual confirmation message is not proof that a real request was saved. Production request systems need appropriate processing, security and authorised access controls, not just a designed form.

10 / Evaluate on different devices

Responsive and mobile usability

A responsive page should be usable at narrow and wide screen sizes. On a phone, navigation may wrap or stack and service cards may become one column. Text should not require scrolling the entire page sideways.

When testing, ask: Can you see the main action? Can you read the text without zooming excessively? Can you reach all form fields? Do buttons have enough space to select accurately? Does the page remain understandable when text is enlarged?

Try a phone-width browser window and a wider desktop window. A screenshot alone cannot test keyboard interaction or whether a visitor understands the labels.

11 / Test systematically

A simple website evaluation method

  1. Select a page and user task. Example: find the opening hours of a fictional college library.
  2. Make a success criterion. The correct hours should be found within a short navigation path.
  3. Attempt the task. Use ordinary navigation first; observe where information is unclear or hidden.
  4. Apply a checklist. Examine navigation, readability, keyboard access, mobile layout and other basic points.
  5. Record evidence. Write where the problem occurs and what happens to the visitor.
  6. Suggest a change. Explain how one specific improvement would help.
Example: “Opening hours were located only under ‘About → Administrative’, which a first-time visitor may not expect. Add an ‘Opening Hours’ link under Services and on the homepage.”

Do not claim a task-time measurement or a success rate unless you actually recorded those observations during a test.

12 / Decide what to fix first

Report findings and prioritise improvements

Not every issue has the same effect. A spelling error in a low-use paragraph is usually less urgent than a broken catalogue search button.

PriorityTypical impactExample
HighBlocks a key task or creates a serious access barrierRequest form cannot be completed using a keyboard
MediumCreates confusion or extra effortOpening hours are under an unclear menu heading
LowMinor inconvenience without blocking tasksInconsistent spacing between two secondary sections

A useful finding includes four parts: location → issue → user impact → recommendation. For instance, “On the library homepage, the catalogue search is below several large banners. A student may overlook it. Move the search field near the main heading.”

13 / Connect the skills to your field

Applications in libraries and records centres

Library and Information Studies

Evaluate whether visitors can find the catalogue, digital resources, study-space rules, borrowing services and opening hours. Check clear search labels, readable results, and whether links reveal the correct destinations.

Sample task: find the borrowing period for a fictional textbook.

Records Management Systems

Evaluate whether a public portal explains available records, request eligibility, procedures and contact channels. Check whether unclear office codes or confidentiality risks could mislead visitors.

Sample task: find how to request a fictional public service report.

For real records services, user-friendly navigation must work alongside proper classification, retention policies, legal requirements and access controls. Design should never expose information that a visitor is not authorised to see.

Review Questions — Unit 9

Use these questions to revise the unit. Answer in your own words and complete the practical examples where requested.

  1. Define website usability. Explain how it differs from user interface (UI) design and user experience (UX).
  2. Identify three typical visitors to a library or records-centre website and one task each might perform.
  3. Explain how clear navigation, meaningful link names and consistent page layouts help visitors.
  4. What is visual hierarchy? Explain how typography, spacing and colour can improve readability.
  5. Name the four accessibility principles (POUR) and explain one example of each.
  6. Explain why keyboard navigation, visible focus and descriptive alternative text are important.
  7. A form displays only “Error” after submission. Explain why this feedback is weak and write a more helpful message.
  8. A website looks good on a computer but its menu is difficult to use on a phone. Identify two possible problems and recommend improvements.
  9. Describe a simple method for evaluating a website, including a user task, observation and recording a finding.
  10. Distinguish an observed usability problem from a recommendation. Give an example of each.
  11. A records-centre website hides its request instructions under an unclear menu label. Describe the problem, its effect and a specific improvement.
  12. Evaluate a fictional or public library/records-centre webpage using three criteria: navigation, readability and accessibility. Record one finding and a justified recommendation for each.

18 / Simple independent task

Assignment 9 — Three findings and recommendations

Evaluate a fictional library or records-centre webpage from the comparison activity. Identify three usability issues. For each one, write:

  1. The problem you observed.
  2. Why it may make the visitor's task difficult.
  3. One clear improvement you recommend.

Prepare: one page containing a small three-row table or three short paragraphs. No HTML coding is required for this assignment.

Use the provided fictional examples. Do not evaluate confidential records or real users' personal information.

19 / Remember the essentials

Unit 9 summary

  • Usability asks whether a particular visitor can complete an important task.
  • Clear navigation and familiar labels improve findability.
  • Readable content, spacing and visual hierarchy help people scan webpages.
  • Accessibility requires more than pleasing colours; keyboard access, labels and text alternatives matter.
  • Responsive layouts should remain understandable and usable on narrow screens.
  • Useful evaluation findings connect a problem to its impact and a specific improvement.
  • A beginner checklist is a starting point, not a formal audit or guarantee of accessibility.
